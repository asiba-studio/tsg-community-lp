# LP構築ガイド — microCMS × Next.js/Vercel 共通アーキテクチャ

asiba-studio-hp の実装で踏んだ罠と固まった設計判断のうち、**他のLPにも転用できる部分だけ**を抜き出した指示書。サイト固有の意匠（後述）は意図的に除外している。

固有名詞は一般化してある：`project`/`article` は「一覧＋詳細を持つコンテンツタイプA/B」の意味で使い、実際のLPでは好きな名前を付けてよい（`works`/`texts`のような凝った呼称にする必要はない）。

---

## 1. CMS設計（microCMS）

### 1.1 リッチテキスト本文フィールドの扱い（richEditorV2）

本文フィールド（`body`相当）は素のHTML文字列として返る。LP側でパースして独自レンダラーに通す設計を前提にする。

**figcaption のプレフィックスコマンド**
画像キャプションの先頭に埋め込み式のコマンドを許可すると、著者側で細かいレイアウト指定ができる。例：

```
[2]この写真のキャプション        → 2枚横並びグリッド
[auto]この写真のキャプション     → 画像本来のアスペクト比
[120px]この写真のキャプション    → 固定幅
```

- パース時に **先頭の `[...]` を正規表現で抽出・除去してから** 実際のcaptionテキストとして表示すること。除去し忘れると`[2]`のような文字列がそのまま画面に出る事故になる。
- コマンドの有無で分岐するのはレンダラー側のロジックであり、CMSスキーマ上は普通のテキストフィールドのまま — 特別なフィールド型は不要。

**ブロック要素はテキストの流れから分離する**
`table` / `pre` / `hr` はインラインの段落と同じ幅で描画すると崩れる（`table-layout`の幅膨張、コードブロックの折り返し等）。本文全体を1回パースする際に、これらを「ブロックチャンク」として地の文チャンクとは別種として抽出し、レイアウト上も別カラム幅（本文カラムいっぱい）で描画する。

**セクション分割は`<hr>`に依存させない**
「`<hr>`で本文を複数セクションに割ってレイアウトエンジンを複数回呼ぶ」設計は複雑になりがちで、実際に廃止して「文書全体を1回だけパースし、単一のレイアウトコンポーネントに全チャンクを渡す」方式に変えた。`<hr>`は装飾のブロックチャンクとして残るだけでよい。セクション番号を数えたいだけなら、パース結果ではなく本文中の`<hr>`個数を数えれば足りる。

**blockquoteは専用コンポーネントを作らない**
Tailwind Typography（`@tailwindcss/typography`）の `prose-blockquote:*` 修飾子で上書きするだけで十分。自動スマート引用符（`quotes` + `::before`/`::after`）は大体のデザインで邪魔になるので `before:content-none` 等で明示的に打ち消す。

**注釈参照システム（note）**
本文中に `[*1]`のような参照マーカーを埋め込み、別フィールド（`notes`配列、`num`/`title`/`body`を持つ）と対応させる方式は汎用的に使える。PC は横に注釈カラムを出し、モバイルはタップでモーダル、という出し分けが標準的。

**話者タグ（対談・インタビュー形式の記事）**
対談・インタビュー記事で「ここから先は誰の発言か」を本文中に埋め込みたい場合、CMSのリッチテキストエディタ側でパラグラフに専用のスタイル/クラス（例: `speaker`）を割り当てられるようにしておき、フロント側はそのクラスを持つ要素を検出して発言者ラベルとして地の文と別スタイル（色を変える・上マージンを広めに取る等）で描画するだけで十分機能する。

- 話者名は**プレーンテキストの自由入力のままでよい**。記事の`credits`配列のような構造化データと名寄せ・突き合わせをする必要はない——著者が本文中に手打ちした名前をそのままラベル表示するだけの割り切った設計で十分運用できる（構造化リンクを持たせる設計にすると、credits側の表記揺れで本文側のラベルと食い違う事故の方が起きやすい）。
- 実装は「特定クラスを持つ要素を検出してスタイルを変えるだけ」なので、1.1で述べたDOM解析パーサーの中に判定を1行足すだけで済む。専用のカスタムフィールドやコンポーネントは不要。

**まとめ：この手のパーサーは1箇所に集約する**
DOM解析の純粋関数（タグ判定・チャンク抽出等）は `'use client'` を付けないモジュールに集約すること。Server ComponentとClient Componentの両方から呼べる必要があるため、`'use client'`ファイルからexportした関数をServer Componentから呼ぶとランタイムエラーになる（Reactのバンドル境界の制約）。

### 1.2 selectフィールドの罠

microCMSの `select` フィールドは **`multipleSelect: false` でも配列で返る**（例: `["draft"]`）。`===` で比較すると常にfalseになる。**必ず `.includes()` で判定すること**。他のフィールド型移行時にも忘れがちなので、CMSラッパーの型定義コメントに明記しておくとよい。

### 1.3 「診断図＋凡例」のような複合カスタムフィールド

「画像1枚＋その画像に対する注釈リスト」のような組み合わせは、素の画像フィールドではなく `custom` フィールド（`{ image, legends: Note[] }` 相当）として1つにまとめておくと、詳細ページ側の取得・型付けが楽になる。画像とメタ情報を別々のフィールドに分けると、対応関係を実装側で管理する必要が出て事故りやすい。

### 1.4 「同じエンドポイントでも本質的に別物」のコンテンツ種別

1つのコンテンツタイプ（例: `project`）の中に、実態としては全く異なる情報構造・詳細ページレイアウトを持つサブタイプが混在することがある（例: 「自社主導のプロジェクト」と「協業プログラム参加者のプロジェクト」）。

- 無理に1つの詳細ページテンプレートに両方詰め込むと条件分岐が肥大化する。**判別フラグ（select、単一値・複数値どちらでも可）を1つ立てて、詳細ページのルーティング/レンダリングを丸ごと分岐**させる方が保守しやすい（`isXxxProject`のような単純な判定関数1つに集約）。
- 判別フィールドの命名・値は最初に決め切ってしまうこと。後から「実は3種類あった」と分かると判定ロジックが各所に散らばって表記ゆれ（アンダースコア/ハイフン等）で壊れやすい。同じ意味のfieldIdを複数箇所で直接文字列比較している場合は要注意——1箇所にexportした定数を参照する形にする。

### 1.5 関連コンテンツ（relation）

`related_xxx` のような参照フィールド（outgoing）を持たせるのは簡単だが、「Aから貼ったリンクをBの詳細ページにも逆向きに表示したい」（incoming）場合はCMS側に自動的な逆引きは無いので、フロント側で「全件を舐めてrelated_xxxに自分のIDを含むものを探す」ような逆引き取得関数を別途用意する必要がある。

### 1.6 マルチサイト配信フィルタ（`relationList` で「どのLPに出すか」を管理する場合）

複数のLPが同じCMSを共有し、コンテンツごとに「このLPには出す/出さない」を管理したい場合、`relationList`（複数コンテンツ参照）フィールドで「サイト」コンテンツを参照させる設計が使える。ただし：

- microCMSの絞り込みは **`[contains]`のみ公式サポート**。絞り込めるのは参照先の**コンテンツID**のみで、`publish_sites[contains]<site-id>` の形で書く。配列内のどれか1つが一致すればヒットする。
- 一覧取得のラッパー関数（SDKクライアントの薄いラップ）に、このフィルタを**デフォルトで自動付与**しておき、必要な箇所だけバイパスできるオプションを持たせるのが良い。新規実装のたびに各ページで手動フィルタを書くと漏れが出る。
- 全件取得ヘルパー（microCMSの`limit`上限を超えて offset ループする関数）を作る場合も、内部で同じ一覧取得関数を呼ぶようにして、フィルタが自動的に効くようにしておく。

### 1.7 スキーマの正本は運用専用リポジトリに置き、各LPはそれを参照する

複数のLPが同じCMSサービスを共有する構成（1.6）では、CMSのAPIスキーマ（フィールド構成・selectItems等）の正本を**CMS運用専用リポジトリのschemas/配下**にスナップショットとして持たせ、各LP側はそれを参照する形にしておくと、フィールド定義がLPごとにドキュメント化されて乖離していく事故を防げる。

- 各LPのリポジトリにも同様のスナップショットを置いてよいが、**どちらが正本かを明記**しておくこと（運用リポジトリのschemas/を正とし、LP側は参照用のコピーと位置付ける）。乖離した場合は運用リポジトリ側を信じる。
- スキーマ変更（フィールド追加・selectItemsの編集）自体はCMS管理画面で行う運用が基本（MCPツール経由でも不可な場合が多い）。運用リポジトリ側で変更後、スナップショットを更新し、各LPはそれを見て型定義・実装を追随させる。
- コンテンツの登録・移行・一括更新のような「フロント実装と無関係な運用作業」も、この専用リポジトリに切り出しておくと、LP側のリポジトリが運用スクリプトで肥大化するのを防げる（LP側でのCMS利用はスキーマ・データ形状の参照用途に限定する）。

### 1.8 統制語彙・タクソノミーは「使われるか」を先に見極める

「テーマ別の共通キーワード」のような統制語彙フィールドを設計しても、コンテンツ総数が少ないサイトでは十分な母数が集まらず、フィルターUIとして機能しないことがある（実際にこのプロジェクトでも不採用になった）。

- **フィールド自体・データ・付与作業は捨てなくてよい**（将来別の見せ方で使う可能性があるため）が、無理に日の目を見せようとしない。採用を保留する判断そのものを設計判断として記録しておく。
- 教訓：小規模サイトでは、統制語彙よりも「事業区分」のような**すでにCMS上にある少数の値でのフィルタ**の方が実用的なことが多い。最初から凝ったタクソノミーを作り込まない。

### 1.9 下書きプレビュー（draftKey方式）

Next.jsの `draftMode()` cookie に依存せず、**URLに含まれる`draftKey`の保持自体を閲覧権限とする**設計。

- 利点：協業先に最終URL（`/projects/{id}?draftKey=...`）をそのまま転送すれば、cookie無しの別ブラウザ・別端末でも下書きが開ける。
- トレードオフ：そのURLがどこかに漏れた場合、追加の認証なしに即座に閲覧可能になる。社外共有前提のワークフローではこちらを取る価値があるが、機密性の高いコンテンツには不向き。cookie必須方式（`draftMode()`）と天秤にかけて選ぶこと。
- 実装パターン：CMS側の「画面プレビュー」設定に `/api/draft?secret=...&contentId={CONTENT_ID}&draftKey={DRAFT_KEY}&type=<endpoint>` を登録 → `/api/draft`ルートがsecret照合後に `/<type>/{id}?draftKey=...` へredirect → 詳細ページ側は`draftKey`クエリがある時だけ`getDetail(endpoint, id, { draftKey })`を呼ぶ。
- 一覧ページのように静的ISRを維持したいページで、個別コンテンツだけ下書きプレビューしたい場合（例: モーダル表示のみで詳細ページを持たないコンテンツタイプ）は、`searchParams`をpage.tsx側で読むとページ全体が動的レンダリング化されてしまう点に注意。専用の薄いAPIルート＋Client Componentマウント時fetchで迂回する。

### 1.10 Webhook revalidation

- CMSのfetchラッパーにデフォルトで `next: { revalidate: <秒数>, tags: [endpoint, ...] }` を付与しておく（SDKの`customRequestInit`はfetchの`RequestInit`にマージされるのでNext.jsのData Cacheオプションがそのまま効く）。
- タグは **エンドポイント単位** + **個別コンテンツ単位**（`${endpoint}:${contentId}`）の2段構えにしておくと、Webhookペイロードにcontent idがある場合は該当コンテンツだけをピンポイントで失効できる。
- Webhookエンドポイントは共有シークレットで署名検証（HMAC-SHA256、`x-microcms-signature`ヘッダー等）してから401判定。
- Next.js 16では `revalidateTag(tag, profile)` の第2引数が必須。外部更新を即時反映させたい場合は `{ expire: 0 }` を使う。
- 秒数ベースのISR（例: 1時間）はWebhookが届かなかった場合の保険として併用する（belt-and-suspenders）。どちらか一方だけに依存しない。
- 下書きプレビュー用のfetchは、このタグ付きキャッシュから完全に除外し `cache: 'no-store'` にすること。同じタグの下に下書きコンテンツがキャッシュされて他の閲覧者に漏れるのを防ぐため。

## 2. Next.js / Vercel アーキテクチャ

### 2.1 データ取得レイヤーを1箇所に集約する

CMS SDKクライアントの薄いラッパーを1ファイルにまとめ、以下を一元管理する：

- publish_sitesのようなデフォルトフィルタの自動付与
- revalidateタグの自動付与
- `limit`上限を超えて全件取得するヘルパー（offsetループ）

各ページ側は素直にこのラッパーの標準動作に任せてよい設計にしておくと、新規実装時の実装漏れ・表記ゆれ事故を防げる。

### 2.2 ISR + オンデマンドrevalidateの二段構え

1.10で述べた通り。「Webhookで即時反映、時間ベースはフォールバック」という二段構えを標準構成にする。

### 2.3 多言語対応（DeepL等の機械翻訳を使う場合）

- 一覧・フィルターUIのようなClient Componentは、`lang?: 'ja' | 'en'` propを持たせて多言語間で**共用**する。言語ごとに別実装を作らない。
- 本文翻訳が必要な詳細ページだけ、言語別のServer Component（例: `XxxBody.tsx` / `XxxBodyEn.tsx`）に分離し、翻訳APIをそこで呼ぶ。
- 翻訳クライアントのインスタンスは**初回呼び出し時に遅延生成**する。モジュールロード時に生成すると、ビルド時のページデータ収集フェーズでAPIキー未設定のままインスタンス化されビルドが落ちることがある。
- 翻訳APIの呼び出しが失敗しても例外を投げず、**元の言語のHTMLをそのまま返す**フォールバックにする。複数件を`Promise.all`で並列翻訳する場合、1件の失敗が他の成功分まで巻き込まないようにするため。
- 翻訳結果は**本文のハッシュ値をキャッシュキーにする**（`updatedAt`のようなタイムスタンプをキーに使わない）。本文と無関係なフィールド編集でも更新日時は変わってしまい、無駄な再翻訳が走るため。キャッシュはハッシュが変わらない限り無期限に保持してよい。

### 2.4 画像ドメインの許可リスト

CMSの画像配信ドメインのみを`next.config`の許可リストに追加する。ワイルドカードで全ドメイン許可にしない。

### 2.5 環境変数チェックリスト

LP構築の初期段階で以下を洗い出し、`.env.local`とVercel側の両方に設定する：

```
MICROCMS_SERVICE_DOMAIN / MICROCMS_API_KEY     # CMS認証
MICROCMS_WEBHOOK_SECRET                    # Webhook revalidation署名検証用
MICROCMS_DRAFT_SECRET                      # Draft preview用
RESEND_API_KEY 等                     # 問い合わせフォームのメール送信を実装する場合
DEEPL_API_KEY                         # 多言語対応する場合
```

### 2.6 複数LPで同一CMSサービスを共有する場合の環境変数命名

1.6の`publish_sites`によるマルチサイト配信フィルタとセットで使う運用。1つのCMSサービスを複数のLP（別々のNext.js/Vercelプロジェクト）が共有する構成では、以下4つの**環境変数名をどのLPでも統一する**：

```
MICROCMS_SERVICE_DOMAIN
MICROCMS_API_KEY
MICROCMS_WEBHOOK_SECRET
MICROCMS_DRAFT_SECRET
```

- 統一すべきは**キー名のみ**。値は各LPの担当者（人間）がVercel/`.env.local`にその都度手動で入力する運用でよく、コード側は環境変数名を読み取るだけで済むようにしておく。
- `MICROCMS_WEBHOOK_SECRET`/`MICROCMS_DRAFT_SECRET`を全LPで同じ値にするか、`MICROCMS_API_KEY`をVercel（production）と`.env.local`（開発用）で異なる値にするか——といった「値をどう使い分けるか」は運用する人間側の裁量であり、**コード実装がその使い分けを意識する必要はない**。キー名さえ統一されていれば、CMSラッパーの実装はLP間でそのままコピーして使い回せる。

### 2.7 Adobe Fonts（Typekit）

Typekit経由でWebフォントを読み込む場合、**特定のグリフ（矢印記号等の特殊文字）がキットに含まれておらず別書体にフォールバックする**ことがある。フォールバック調査は`font-feature-settings`を含めて事前に確認し、含まれないグリフは：

- Unicode文字ではなくインラインSVG（`fill="currentColor"`で親のtext colorを継承）で代替する
- 画像ファイル（`<img>`）での代替は再着色ができず柔軟性に欠けるため避ける

variable fontでない書体には `font-stretch` のような可変軸プロパティは使えない。書体を選定する段階でvariable対応かどうかを確認しておく。

### 2.8 proseのカスタマイズ方針

Tailwind Typography（`prose`）はそのままでは大抵のデザインに合わないので、**LPごとに`prose-*`修飾子を上書きする専用の定数ファイル**（配列 or クラス文字列）を1つ作り、リッチテキストをレンダリングする全コンポーネント（本文詳細ページ・モーダル等）で共有する。

- table: `<thead>`を持たない構造を前提に、`th`/`td`両方に明示パディングを付与し、行区切りはborder-bottomで表現するなど、CMS側のリッチテキストエディタが吐くHTML構造に合わせて個別調整が要る
- pre/code: Typography標準のダークテーマ配色をそのまま使うと大抵浮くので、サイトの意匠に合わせて上書きする
- blockquote: 1.1参照
- 新しいリッチテキストレンダラーをLP内に増やすときは、この共有定数を必ずimportする（インラインで似たようなクラスを都度書かない）

### 2.9 404 / エラー / 下書きプレビューの状態ページはシンプルでいいので必ず用意する

LP初期構築時に後回しにされがちだが、凝ったデザインは不要なので**最低限のものを最初に作っておく**。

**404（`app/not-found.tsx`）/ エラー（`app/error.tsx`）**
Next.jsのApp Routerがファイル名で自動的に使う予約ファイル。放置するとNext.jsのデフォルト画面がそのまま出てしまう。

```tsx
// app/not-found.tsx — Server Componentのままでよい
import Link from "next/link";

export default function NotFound() {
  return (
    <div className="min-h-screen flex flex-col items-center justify-center text-center">
      <p className="text-7xl">404</p>
      <p className="mt-6 text-sm">PAGE NOT FOUND</p>
      <Link href="/" className="mt-2 underline underline-offset-4">
        BACK TO HOME
      </Link>
    </div>
  );
}
```

```tsx
// app/error.tsx — 'use client' 必須
"use client";
import { useEffect } from "react";

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    console.error(error);
  }, [error]);
  return (
    <div className="min-h-screen flex flex-col items-center justify-center text-center">
      <p className="text-7xl">ERROR</p>
      <p className="mt-6 text-sm">SOMETHING WENT WRONG</p>
      <button
        onClick={() => reset()}
        className="mt-2 underline underline-offset-4"
      >
        TRY AGAIN
      </button>
    </div>
  );
}
```

- `error.tsx`は**`'use client'`必須**（Reactのエラー境界はクライアント側実装のため）。`reset()`でエラー境界をリセットして再レンダリングを試みさせる導線を必ず用意する。
- 固定ヘッダーを持つLPでは、ヘッダー分のスペーサー（例: `h-14 shrink-0`）を先頭に入れて、ページ本文がヘッダーに隠れないようにする。
- 配色・フォントはLPの基本トーンに合わせる程度でよい。本文コンテンツと同等の作り込みは不要——「今何が起きているか」と「離脱・再試行の導線」があれば十分。

**下書きプレビューのバナー（1.9のdraftKey方式とセット）**
下書き閲覧中は画面最上部に固定の小さいバナーを出し、閲覧者が今見ているのが下書きだと常に分かるようにしておく。

- 内容は「DRAFT PREVIEW」のようなラベル + 離脱リンクだけで十分（`z-[100]`程度の最前面、警告色＝サイトの通常UIでは使わない色を使い、誤って本番コンテンツと混同されないようにする）
- 離脱リンクは単純にトップページへの通常リンクでよい。draftKey方式（1.9）はcookieを持たないため、明示的な「プレビュー解除」処理は不要——リンクを踏んで`draftKey`が付いていないURLに移動するだけで自然に外れる

## 3. このサイト固有につき持ち込まないもの

以下はasiba-studio-hp自体の意匠・ドメイン概念であり、他のLPへの指示書には**含めない**：

- **`works`/`texts`のような凝った呼称**。他のLPでは素直に`projects`/`articles`等、そのサイトのドメインに合った名前を付ければよい
